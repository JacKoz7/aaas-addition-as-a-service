## Goal
`digit-8` in D with its own SQLite database, following the reference
behaviour of `digit-0` (ADR-0022) and passing the shared contract test
`make contract-digit-8`. Result: digit 8.

## What Was Done
- **Service `services/digit-8`**:
  - D with LDC 1.42 (DMD front end 2.112) on Alpine 3.24. No dub
    dependencies: Phobos supplies the sockets (`std.socket`), the threads
    (`core.thread`) and the SQLite binding (`etc.c.sqlite3`).
  - Scaffolded with `scripts/new-service.sh digit-8 d`.
  - `src/digit8/server.d`: an accept thread and one druntime thread with a
    256 KiB stack per connection, at most 256 connections, a lingering
    close (200 ms, 16 KiB), a graceful stop. `recv` and `send` retry on
    `EINTR`. Each ended connection thread joins the one that ended before
    it.
  - `src/digit8/http.d`: the framing of `digit-6`, all of it `@safe`:
    - line reading with a byte budget;
    - heads up to 8 KiB (431 above);
    - bodies by Content-Length or chunked, up to 64 KiB (413 above; 400
      for ambiguous framing);
    - keep-alive;
    - reply formatting and the request loop.
  - `src/digit8/api.d`: the contract as `(method, path) → Reply`, called
    under one mutex.
  - `src/digit8/service.d`: configuration, start-up checks, SIGTERM and
    SIGINT through `sigwait`. `src/digit8/app.d` holds only `main`,
    because `dub test` leaves the main source file out of the test build.
  - Also `store.d`, `metrics.d`, `log.d` and `trace.d`.
  - `migrations/0001_digit.sql`: table `digit` with the seed `8|8|9|0`.
  - Tests, 61 `unittest` blocks in all:
    - ddoc documented unit tests in `src/` (the declarations' examples);
    - `tests/digit8_tests/`: the contract and the migrations, the framing
      through a connection double, the server over TCP (keep-alive, stop,
      connection limit, port in use, joined threads), the configuration.
  - `tools/doc_coverage.d`: the documentation gate on the compiler's JSON
    description (`ldc2 -D -X`), down to private declarations.
  - `dub.sdl` (with a static `production` build type), `dscanner.ini`,
    `.editorconfig` (dfmt settings).
- **Image stages**:
  - base: `alpine:3.24.3` with `ldc`, `dub`, `gcc`, `musl-dev`, the
    SQLite and zlib libraries, all pinned;
  - dtools: dfmt and D-Scanner 0.15.2 built from their dub packages;
  - lint: dfmt (the output must equal the file), D-Scanner, builds of
    every target with warnings and deprecations as errors;
  - test: `dub test`;
  - doc-coverage: `tools/doc_coverage.d` and ddoc with `-w`;
  - api-docs: ddoc HTML of the `src` modules with an index;
  - build: the stripped static executable (2.9 MB);
  - runtime: `scratch` with the executable, the migrations and busybox
    `wget`, user 10001; 6.49 MB.
- **Compose**: `digit-8` on the `services` network only, 64m, exec-form
  healthcheck, volume `digit-8-data`.
- **Repository**: the header type `sdl` (`dub.sdl`) in
  `templates/headers/styles.psv`, with `templates/headers/sdl.tmpl`.
- **Documentation**: README, all ten documents of `CLAUDE.md` 6.5.5 with
  real content, API.md (generated sections by `make api-md`), ADR-0030.

- Edge cases on the running container (client container on
  `aaas-services`):
  - **Requests:**
    - a 10-byte body and then a GET: 405 then 200;
    - HEAD: 405 without a body;
    - unknown path: 404;
    - a query string: 200;
    - garbage: 400;
    - heads of 9 000 bytes and of 200 KB: 431;
    - `Content-Length: 70000`: 413;
    - a chunked body and then a GET: 405 then 200;
    - `Content-Length` with `Transfer-Encoding`: 400;
    - HTTP/1.0: `Connection: close`;
    - HTTP/2 preface: 400.
  - **Slow client:** a half-sent request line does not delay another
    client (0.2 ms) and is closed after 10.2 s.
  - **Connection limit:** 256, 257 and 300 connections, 256 answered each
    time.
  - **Resets:** 100 connections reset mid-request, then 200.
  - **Floods:** two clients each opened 256 connections with 1 MB heads.
    - First build: the container was stopped by the memory limit in round
      ten (`OOMKilled=true`). `/proc/1/maps` showed about 2 350 thread
      stacks of exited, unjoined threads (about 25 MiB resident).
    - After the fix: ten rounds, 9–16 MiB after each round, `memory.peak`
      27 MiB, 25 mappings afterwards; the service stayed healthy.
  - **Database:** with table `digit` renamed, `/value` and `/health`
    answered 503, with `no such table: digit` in the error line. After
    the rename back, both answered 200.
  - **Debug log:** `AAAS_LOG_LEVEL=debug` gave the request line with the
    caller's `traceId` and `spanId`.
- Load:
  - 0.037 ms per call on a keep-alive connection;
  - 0.17 ms per call with a new connection;
  - 8 concurrent clients: 4 000 calls in 0.17–0.27 s, no error.
- RAM: 3.2 MiB idle (3.0 MiB after `make up`), 25 MiB with 256 idle
  connections, 16 MiB after the floods (the garbage-collected heap is kept
  for reuse; CAPACITY.md).
- Stop:

  - a restart with the existing volume re-applies no migration.
- Each of these stops the start with exit status 1 and an error log line:

## Decisions
- [ADR-0030](../../adr/0030-digit-8-d-with-phobos.md):
  - LDC on Alpine (DMD has no arm64 build) with Phobos and no dub
    dependencies, instead of vibe.d;
  - the HTTP/1.1 server design of `digit-6`, with `EINTR` retries;
  - each ended connection thread joins the previous one;
  - a static executable on `scratch`;
  - dfmt and D-Scanner built from dub, with two checks off;
  - the documentation gate on the compiler's JSON description;
  - `main` alone in `app.d` for `dub test`.
